## 1. 기존 MES Supabase 프로젝트에 **연차관리 전용 테이블 설치**

1. https://supabase.com/dashboard 에 로그인합니다.
2. 상단에서 **`dnmai0996's Project` (PRODUCTION)** 을 선택합니다. 사진과 같은 기존 MES 프로젝트인지 확인합니다.
3. 화면 왼쪽 메뉴에서 **SQL Editor (SQL 편집기, `>_` 모양)** 를 엽니다.
4. 새 쿼리(New query)를 클릭합니다.
5. ZIP 안의 **`database/01_install_leave.sql`** 전체를 복사하여 붙여넣고 **Run**을 누릅니다. 성공하면 다음 테이블이 생성됩니다.

   - `dnm_leave_state`: 기존 운영상태 전체
   - `dnm_leave_companies`, `dnm_leave_employees`: 회사·직원
   - `dnm_leave_requests`: 연차 신청과 결재 단계·상태
   - `dnm_leave_adjustments`, `dnm_leave_cycle_grants`: 가감조정·발생량 확정
   - `dnm_leave_staff_audit`, `dnm_leave_roster_history`: 변경 및 원본 이력
   - `dnm_leave_test_clear_history`, `dnm_leave_archives`: 이전 작업·삭제 전 안전백업
   - `dnm_leave_work_settings`, `dnm_leave_custom_holidays`: 근무기준·휴일
   - `dnm_leave_sessions`: 로그인 세션
   - `dnm_leave_mes_outbox`, `dnm_leave_mes_config`: MES 작업자 연동 대기열·설정

6. 새 쿼리를 열어 **`database/02_mes_sync.sql`** 전체를 실행합니다. 작업자 자동 연동 **프로그램만 설치**되며 기본값 `enabled=false`로, 실제 MES 테이블을 변경하지 않습니다.
7. `Table Editor`에서 `dnm_leave_`로 시작하는 테이블이 생겼는지 확인합니다. 아직 레코드 수가 0이어도 정상입니다. **기존 MES 테이블을 삭제하거나 이전 SQL을 다시 실행하지 마세요.**

**보안:** 연차 테이블은 RLS 활성화 및 브라우저의 `anon`/`authenticated` 직접 접근 차단으로 설정했습니다. 연차 API는 Netlify 서버에서만 관리자 권한을 확인하고 안전하게 접속합니다. 비밀번호 해시 등 원본 개인정보가 포함되므로 `dnm_leave_state.payload`를 공개 조회하지 마세요.

## 2. 연차관리 Netlify에 Supabase 서버 비밀키만 설정

1. 기존 **연차관리 Netlify 사이트**(MES Netlify 사이트가 아닙니다)에 로그인합니다.
2. Site configuration / Environment variables / Add variable에 아래를 등록합니다.

| 변수 이름 | 넣을 값 | 설명 |
|---|---|---|
| `DNM_LEAVE_SUPABASE_URL` | `https://ohzbtkdxapbmiemdamho.supabase.co` | 위 기존 MES Supabase 프로젝트 화면에서 확인·복사 |
| `DNM_LEAVE_SUPABASE_SECRET_KEY` | **Supabase `sb_secret_…`** | **프로젝트 → Settings → API Keys** 또는 Connect에서 생성·복사한 **Secret key**. 브라우저/GitHub/채팅에 붙이지 않음 |
| `DNM_LEAVE_STORAGE` | **아직 만들지 않거나 `blobs`** | **3단계 백업·이관·검증이 완료되기 전까지 `supabase`로 변경하지 않음** |

**중요:** 신규 Supabase의 `Publishable key` (`sb_publishable_…`)는 서버 비밀키 대신 사용할 수 없습니다. **Secret key는 Netlify 서버 환경변수로만 보관**합니다. 기존 MES가 사용하는 `config.js` 및 MES Edge Function의 설정은 수정하지 않습니다.

## 3. 연차관리 소스코드를 **기존 사이트**에 배포

1. 기존 연차관리 소스코드 폴더를 별도 백업합니다.
2. 제공된 `DNM_Annual_v8_4_Supabase.zip`의 압축을 해제합니다. 그 안에는 `public/`, `netlify/functions/`, `database/`, `scripts/`, `package.json`, `netlify.toml`이 있습니다.
3. 기존 연차관리 GitHub Desktop 저장소에 **ZIP 안의 전체 내용을 병합**합니다. 사용 중인 연차관리 Netlify 사이트가 기존 GitHub 저장소와 연결되어 있어야 합니다.
4. GitHub Desktop → 변경 파일 확인 → Commit → **Push origin** 순서로 진행합니다. 다른 MES 저장소에는 업로드하지 않습니다.
5. Netlify **Deploys**에서 성공 여부를 확인합니다. 정적 파일 폴더는 `public`, 함수 폴더는 `netlify/functions`, Node.js 22입니다.
6. 기존 연차관리 URL을 새로 열고 `Ctrl + F5`를 눌러 새로고침합니다. 관리자 메뉴 `Excel·백업`에 **“운영 DB 이전 · MES 작업자 연계 (v8.4)”**가 보이는지 확인합니다.
7. 관리자 화면에서 **현재 저장소가 “Netlify Blobs”라고 표시되는 것**을 확인합니다. 이 단계에서는 기존 데이터가 여전히 원래 Blobs에 있어야 합니다.

**Netlify 수동 파일 업로드만으로는 서버 함수의 npm 의존성 설치가 누락될 수 있습니다. GitHub 연동 배포를 권장합니다.**

## 4. 실제 운영 데이터 **전체 이관 (서버 백업 → 잠금 → 복제 → 검증)**

작업 시작 전에 직원들에게 연차 신청·결재 일시 중단을 안내하고 운영 데이터 백업을 확보해야 합니다.

1. 기존 연차관리 사이트 관리자 로그인 → **Excel·백업** 이동.
2. **① 전체 JSON 백업 다운로드** 버튼을 클릭하여 PC에 저장합니다.
3. **② 백업 JSON 재선택**으로 지금 받은 **동일한 최신 파일**을 선택합니다. 브라우저가 SHA-256 검증용 해시를 계산합니다.
4. 관리자 현재 비밀번호를 입력하고 확인 문구 **`연차DB이관`**을 정확히 입력한 후 백업 보존 동의에 체크합니다.
5. **③ 운영 데이터 전체를 Supabase에 이관 · 검증** 버튼을 클릭합니다.
6. 서버가 **(a) JSON 최신성 검사 → (b) 별도의 이전 전 백업 저장 → (c) 기존 Blobs 쓰기 동결 → (d) Supabase `dnm_leave_state`에 자료 최초 등록 → (e) 전체 JSON 해시 동일성 검증 → (f) 이전 서버 백업 복제**를 실행합니다.
7. 화면에 “Supabase 이관 검증 완료”가 표시되면 **직원 수, 신청 수, 이력 수, 백업 수**를 확인합니다. 이 단계에서는 **기존 Blobs가 읽기 전용**이므로 다음 5단계를 지체 없이 이어서 진행합니다.

**실패 처리**
- **409 데이터 변경**: 다른 사용자가 저장했거나 선택한 JSON이 최신이 아닙니다. 동결 전에 실패했다면 최신 JSON 다시 백업한 후 반복합니다.
- **423 저장 중지**: 이관 작업 중 기존 Blobs가 이미 동결되었습니다. 직원이 새 요청을 제출하지 않도록 합니다.
- **500/503 데이터베이스 오류**: 환경변수, SQL 01·02 실행 성공, Netlify Functions 로그를 확인합니다. **기존 Blobs를 임의 삭제·초기화·잠금 해제하지 않습니다.** 이미 동결되었다면 같은 백업으로 재실행할 수 있도록 설계되어 있으나, 사전 검사 없이 새로운 자료를 덮어쓰지 마세요.
- 이관 후 자료가 일부 누락되어 보이면 **즉시 운영 전환을 중단**하고, 양측 백업과 `05_verify_leave.sql`로 건수·무결성 비교를 진행합니다.

## 5. DB 전환: 마지막 환경변수만 변경

1. **이관 검증 성공 메시지를 확인한 다음** 기존 연차 Netlify의 Environment variables로 돌아갑니다.
2. `DNM_LEAVE_STORAGE` 값을 정확히 **`supabase`**로 설정합니다.
3. 기존 사이트 **재배포(Redeploy)** 합니다. **새로운 사이트를 만들지 않습니다.**
4. 브라우저에서 다시 로그인하고 **Excel·백업**에서 **“현재 저장소: Supabase PostgreSQL”**을 확인합니다.
5. 직원명부 숫자, 신청·승인 기록, 결재함, 사용자 로그인, 근무기준 및 휴일, Excel 내보내기, JSON 백업이 정상인지 실제 운영 계정으로 확인합니다.
6. Supabase → SQL Editor → `database/05_verify_leave.sql`을 실행하고 **`dnm_leave_state` 1건**, `dnm_leave_employees` 직원 수, `dnm_leave_requests` 신청 건수 및 변경이력 건수가 이전 JSON과 일치하는지 대조합니다.
7. **기존 Netlify Blobs를 삭제하지 않습니다.** Supabase 전환 후 신규 신청이 발생하면 원래 Blobs는 이전 시점의 백업으로만 남게 됩니다. 이전값으로 단순 되돌리는 것은 **전환 후 신규 자료가 사라질 수 있으므로 금지**합니다.

## 6. 연차 신규직원/퇴사 시 MES 작업자 동기화

> **현재 패키지는 자동 동기화 엔진과 안전 대기열까지 구현되었습니다. 실제 MES 작업자 기준테이블의 정확한 이름·필드·자료형은 제공된 MES 운영 설명 자료만으로 확인되지 않았으므로, 기본값은 자동 동기화 “비활성”입니다.** 기존 MES 생산이력을 보호하기 위해 정확한 테이블 확인 없이 임의로 활성화할 수 없습니다.

1. Supabase에서 새 SQL Editor를 열고 **`database/03_check_mes_structure.sql`**을 실행합니다. 이 쿼리는 **메타데이터만 조회**하며 근로자 개인정보 레코드를 출력하지 않습니다.
2. 결과에서 MES 작업자 마스터의 **테이블명, 사번 컬럼, 이름 컬럼, 사용 상태 컬럼**을 확인합니다. 필수 컬럼, 자동 ID/UUID, NOT NULL, 기존 로그인 계정과 작업자 ID의 관계도 확인합니다.
3. MES 작업자 테이블과 로그인 계정 데이터를 별도 백업합니다.
4. `database/04_enable_mes_after_review_TEMPLATE.sql`을 참고해 **본인 운영 MES에 실제 존재하는 이름으로** 매핑 설정을 작성하고 실행합니다. 첨부 샘플의 대문자 표시 `YOUR_...`는 실제 이름이 **아니므로 그대로 실행하지 마세요.**
5. 연차관리에서 **새 직원 등록**(동일한 유일 사번 입력) 후 `Excel·백업 → MES 연계 현황 조회`를 클릭합니다. `UPSERT → synced`라면 작업자 마스터 등록 또는 수정 성공입니다.
6. 연차관리에서 **퇴사일을 현재일 또는 과거일로 저장**하거나 사용 중지하면 `DEACTIVATE → synced`가 되어 MES 작업자 사용상태를 해제하도록 설계되어 있습니다. 작업 실적은 삭제하지 않습니다.
7. 퇴사일이 미래이면 **해당 날짜 도달 후 매일 오전 9:10(한국시간)** 예약 함수를 통해 사용 중지 이벤트를 기록하고 처리합니다. Netlify → Functions에서 `leave-daily-sync`에 **Scheduled** 표시 및 실행 기록이 있는지 확인합니다. 자동 실행은 배포된 운영 환경에서만 발생합니다.
8. `needs_review`가 표시되면 두 시스템의 사번 중복, 다른 이름, 사번 누락, MES 필수 필드 미등록 등을 확인하고 **임의로 다른 근로자의 자료를 덮어쓰지 마세요.** MES 관리자 확인 후 재처리합니다.

**MES 로그인 계정 연계:** 기존 DNM MES v4.9.1은 `dnm-accounts` Edge Function으로 로그인 계정을 별도 연결합니다. 이 패키지는 **작업자 기준정보 신규등록/미사용**을 동기화하지만 MES 개인 비밀번호를 생성·초기화하거나 변경하지 않습니다. MES 관리자의 **“작업자 사용·로그인 관리”**에서 연결 완료 여부를 확인해야 합니다. 동명이인은 MES에서 기존 구분 ID 규칙을 따릅니다.

**MES 실제 테이블 구조가 맞지 않거나 필요한 필드가 더 있다면**, 현재 버전의 일반화된 매핑 함수만으로는 완전 자동화되지 않을 수 있습니다. 연차 자료는 정상 저장되고 MES 이벤트는 `error` 또는 `needs_review` 상태로 보류되며, 운영 테이블 스키마를 반영한 추가 변경이 필요합니다.

**처음 이관된 기존 직원은 MES로 일괄 재등록하지 않습니다.** 이미 MES에 있는 사람을 중복 생성하지 않기 위한 조치입니다. 신규/퇴사 등록 등 **전환 후 변경분부터** MES 동기화 대상입니다.

## 7. 사후 연차 신청 규정: 과거 2영업일

직원이 연차 신청 화면을 열면 서버에서 **한국 표준시(KST) 오늘 기준으로 2영업일 전** 날짜를 계산하여 최소 신청일로 표시합니다. 토요일/일요일, 대한민국 공휴일·대체휴일, 연차관리 프로그램에 입력된 회사 휴무일은 영업일 계산에서 제외합니다.

예를 들어 회사 휴일이 없는 **2026년 11월 9일(월)** 기준으로 최소 신청 가능일은 **2026년 11월 5일(목)**입니다. 2026년 11월 6일(금), 11월 5일(목) 사용분을 뒤늦게 신청할 수 있으나, 11월 4일(수) 사용분은 거절합니다. 주말 자체의 연차 차감 여부는 기존 근무일 판단 로직을 따릅니다. **시간 단위·반차·하루/기간 신청 모두 최소일 검사**가 적용되며, 과거 날짜라는 이유만으로 승인 처리가 생략되지는 않습니다.

사후 신청한 기록에는 실제 신청 시각이 유지됩니다. 회사 규정에 따라 사유를 기록하도록 지도하고, 별도의 법정/취업규칙·연차사용촉진 규정 준수 여부는 인사담당자가 판단해야 합니다.

## 8. 운영보안·백업·복구 권고

- **매일** Supabase 자동 백업 정책·보유량을 확인하고, 정기적으로 앱의 관리자 JSON 백업을 외부에 보관하세요. 화면의 Supabase **Last Backup: No backups** 표시는 현재 해당 프로젝트에서 플랫폼 자동 백업을 보장할 수 없다는 신호입니다. 무료요금제의 자동백업 지원 여부는 계정/요금제에서 직접 확인하십시오.
- MES와 연차가 같은 프로젝트를 쓰므로 **연차 쿼리·저장·스토리지 부하가 기존 MES에도 영향을 줄 수 있습니다.** 용량/요청수/프로젝트 상태를 모니터링합니다.
- 사용자는 별도 시스템에서 로그인하므로 작업자 상태를 연계하더라도 **MES/연차 로그인 세션이 동일해지는 것은 아닙니다**.
- 새로 배포되는 모든 함수를 Netlify에 정확히 배포해야 합니다. 데이터베이스 SQL만 실행하고 기존 함수로 접속해도 DB 이전되지 않습니다.
- 기존 기능은 41개 그룹, v8.4 신규 기능은 9개 자동 테스트를 통과했으나, **실제 MES 운영 DB와 Netlify 사이트에서의 실자료 이관·부하 테스트는 이 환경에서 수행하지 못했습니다.** 운영 최종 적용은 반드시 관리자 검수 후 진행하십시오.
- 긴급복구 시 **기존 Blobs 상태, PostgreSQL 상태, 전환 이후 발생한 신규 신청·결재**를 비교하지 않고 저장소 설정만 되돌리면 데이터가 손실될 수 있습니다. 전문가의 데이터 병합/검증 후 복구합니다.
